===============================================================================
 Trap29_RawBytes - CDB debug analysis
===============================================================================

QUESTION
  do raw bytes become a `Record` merely because the storage has the right size and alignment?


SHORT ANSWER
  no. This trap demonstrates the correct protocol: `std::construct_at` begins the lifetime and `std::destroy_at` ends it. The storage remains before and after; the `Record` lifetime exists only between those calls.

-------------------------------------------------------------------------------

1. Read the source first


 1  #include <cstddef>
 2  #include <iostream>
 3  #include <memory>
 4  #include <string>
 5  struct Record { explicit Record(int n):name("record"),number(n){} std::string name; int number; };
 6  int main(){ alignas(Record) std::byte storage[sizeof(Record)];
 7      auto* candidate=reinterpret_cast<Record*>(storage);
 8      Record* object=std::construct_at(candidate,7); // BP
 9      std::cout<<object->name<<':'<<object->number<<'\n';
10      std::destroy_at(object); // BP
11  }


   Entity    Meaning   
  -------------------------------------------------------------------------------  -------------------------------------------------------------------------------  
   `storage`    raw, aligned bytes; not yet a `Record`   
   `candidate`    address where a `Record` may be constructed   
   `object`    valid only after `construct_at` and before `destroy_at`   

-------------------------------------------------------------------------------

2. Build without a sanitizer

Use the existing `Trap29_RawBytes.exe`. There is no `_unsafe` sibling: this is the correct raw-storage protocol, not a contrasting anti-pattern branch.

-------------------------------------------------------------------------------

3. Start CDB

Break at lines 8, 9, and 11. `$t0` pins the storage address so the same bytes are inspected before construction, during the live lifetime, and after destruction.

5. Why there is no unsafe target

`Trap29_RawBytes_unsafe.exe` is absent. Trap29 demonstrates the correct protocol: show storage before construction, a live object after construction, and storage remaining after destruction while the `Record` lifetime no longer exists.

-------------------------------------------------------------------------------

6. What the measurements prove

   Measurement    Before `construct_at`    After `construct_at`    After `destroy_at`   
  -------------------------------------------------------------------------------  -------------------------------------------------------------------------------  -------------------------------------------------------------------------------  -------------------------------------------------------------------------------  
   pinned address    `957bfbf8e8`    same    same   
   `address & 7`    `0`    same    same   
   `object` local    `0xcccc...`    storage address    stale value only   
   typed view    invalid    `Record`, `number=7`    invalid   
   bytes    `cc cc ...`    contains `record` and `07`    bytes remain, lifetime ended   

The divergence is storage versus lifetime. Storage exists for the whole function; the `Record` exists only between the two library calls.

-------------------------------------------------------------------------------

7. Command reference used here

   Command    Why type it   
  -------------------------------------------------------------------------------  -------------------------------------------------------------------------------  
   `r $t0 = @@c++(&storage[0])`    pin one storage address across all stops   
   `db @$t0 L40`    inspect bytes without claiming a live object   
   `dt Trap29_RawBytes!Record @@c++(object)`    view the live object after construction   
   `?? object->number`    read a member while lifetime is active   
   `? @$t0 & 7`    check the storage address alignment
