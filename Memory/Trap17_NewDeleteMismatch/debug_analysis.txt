===============================================================================
 Trap17_NewDeleteMismatch - CDB debug analysis
===============================================================================


QUESTION
  if a pointer value is valid, can any deallocation expression release it?


SHORT ANSWER
  no. The deallocator must match the way storage and lifetime were created: new[] with delete[], malloc with free, and placement new with an explicit destructor call but no delete.




-------------------------------------------------------------------------------
 1. READ THE SOURCE FIRST
-------------------------------------------------------------------------------


main.cpp (47 lines). Three variants run in sequence.

 6  struct Widget { int value{1}; ~Widget() = default; };
 8  // Type 1: new[] paired with scalar delete.
 9  void array_form_mismatch() {
10  #if defined(RUN_UNSAFE_EXAMPLE)
11      auto* p = new Widget[3];
12      delete p; // BP: allocation used new[]; deallocation must use delete[].
13  #else
14      auto p = std::make_unique<Widget[]>(3); // Owner remembers delete[].
15      std::cout << "array: " << p[0].value << '\n';
16  #endif
17  }
20  void allocator_family_mismatch() {
21  #if defined(RUN_UNSAFE_EXAMPLE)
22      auto* p = static_cast<Widget*>(std::malloc(sizeof(Widget)));
23      delete p; // BP: malloc storage must be released with free, and was never constructed.
24  #else
25      auto p = std::make_unique<Widget>(); // One family: new/delete via the owner.
26      std::cout << "family: " << p->value << '\n';
27  #endif
28  }
31  void placement_new_mismatch() {
32      alignas(Widget) unsigned char buffer[sizeof(Widget)];
33      Widget* p = new (buffer) Widget{}; // BP: no allocation happened; only construction.
34  #if defined(RUN_UNSAFE_EXAMPLE)
35      delete p; // BP: frees stack storage that operator new never returned.
36  #else
37      std::cout << "placement: " << p->value << '\n';
38      p->~Widget(); // Destroy explicitly; the buffer is released by its own scope.
39  #endif
40  }

  Variant                       Allocation/lifetime event     Correct release
  array form                    new Widget[3]                 delete[]
  allocator family              std::malloc only gives raw storage  std::free; construction would require placement new
  placement new                 constructor runs in caller-owned buffer  p->~Widget(); no deallocation expression

 2. BUILD WITHOUT A SANITIZER
-------------------------------------------------------------------------------


cmake -S . -B build\cdb -DTRAPS_BUILD_UNSAFE=ON -DTRAPS_SANITIZER=none
cmake --build build\cdb --config Debug --target Trap17_NewDeleteMismatch Trap17_NewDeleteMismatch_unsafe

ASan can catch many deallocation mismatches, but the placement-new case is also a lifetime protocol lesson: construction and destruction must be paired explicitly even when no heap allocation happened.

-------------------------------------------------------------------------------
 6. WHAT THE MEASUREMENTS PROVE
-------------------------------------------------------------------------------


  Variant                       Evidence captured             Why the unsafe deallocator is wrong
  array                         three adjacent Widget values at p  scalar delete does not match new[]
  family                        malloc block contains 0xCD and no constructed Widget  delete expects a new-created object
  placement                     p == &buffer on the stack     delete may only deallocate storage returned by operator new

Debug fill bytes are a Debug CRT courtesy, not a language guarantee: 0xCD is allocated but uninitialized, 0xFD is a guard band, 0xDD is a freed CRT block, and 0xFEEEFEEE is freed Win32 heap memory. Release builds need not write any of them.
