===============================================================================
 Trap31_ShallowCopy - CDB debug analysis
===============================================================================


QUESTION
  if a copied object prints the same text as the original, does that prove the copy owns its own resource?


SHORT ANSWER
  no. The raw pointer member must be inspected in both objects. Identical pointer values mean two owners and two delete[] calls. The Rule of Three and Rule of Zero variants show the two standard repairs.




-------------------------------------------------------------------------------

-------------------------------------------------------------------------------

-------------------------------------------------------------------------------
 2. BUILD WITHOUT A SANITIZER
-------------------------------------------------------------------------------


cmake -S . -B build\cdb -DTRAPS_BUILD_UNSAFE=ON -DTRAPS_SANITIZER=none
cmake --build build\cdb --config Debug --target Trap31_ShallowCopy Trap31_ShallowCopy_unsafe

The debugger is the right first tool because this trap is about object design and ownership. ASan can diagnose the eventual double free, but it does not explain why the class design created two owners.

-------------------------------------------------------------------------------
 6. WHAT THE MEASUREMENTS PROVE
-------------------------------------------------------------------------------


  Variant                       Address evidence              Interpretation
  Broken unsafe                 a.data and b.data are both 1f49b4670a0  two owners, two future delete[] calls
  Rule of Three                 a and b store different char* values  value copy duplicates the buffer, not the pointer
  Rule of Zero                  RuleOfZero contains std::string data_  ownership is delegated to a correct member

Addresses differ every run. Do not compare digits across captures; compare whether two owners inside the same capture hold identical or different addresses.
